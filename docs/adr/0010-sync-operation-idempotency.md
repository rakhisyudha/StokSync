# ADR 0010: Replay durable synchronization operation outcomes

- Status: Accepted
- Date: 2026-09-13

## Context

A mobile client can lose a response after the server has committed an
operation. It must therefore be safe to resend the same operation without
creating a second movement, product revision, balance update, or change-log
entry. The outcome must also be stable for rejected operations: retrying a
validation or domain conflict must not make the result depend on a later
canonical state.

The sync endpoint processes operations independently, so the idempotency
boundary must cover each operation rather than the whole HTTP batch. The
operation identity is the client-generated `op_id` in the authenticated device
scope.

## Decision

Use a durable PostgreSQL idempotency record keyed by `(device_id, op_id)` in
`sync_ops`.

- Reserve the composite key with `INSERT ... ON CONFLICT DO NOTHING` inside
  a transaction that is scoped to the authenticated user and registered device.
- When the reservation is new, apply the operation, update any rebuildable
  projection, append its change-log entry when the operation is accepted, and
  serialize the resulting `OperationResult` into `sync_ops.response` before
  committing. Accepted and terminal rejected results are both durable outcomes.
- The reservation, canonical mutation, projection update, change-log entry,
  and finalized operation result commit together. An unexpected failure rolls
  back the reservation and all related writes, so a later delivery can retry
  the operation rather than observe a partial result.
- When the composite key already exists, read the stored row using the
  authenticated `(user_id, device_id, op_id)` scope, validate the stored result,
  and replay that original operation outcome. Do not validate or apply the
  incoming payload again, allocate a new change sequence, update a balance, or
  overwrite the stored response.
- A missing, malformed, or scope-mismatched stored response is an internal
  consistency failure; it is not permission to apply the incoming operation.

This records the operation result, not a frozen copy of a later change-feed
page. The current sync request still reads its account-scoped page from the
request cursor after operation processing.

## Consequences

- A timeout or dropped response can cause duplicate delivery at the transport
  level, but it cannot duplicate the logical domain operation.
- Rejected intent remains inspectable and deterministic because the original
  structured reason and canonical state are replayed on later delivery.
- `sync_ops` is retained as synchronization audit data and must not be treated
  as a transient request cache.
- Operation identifiers must remain stable across retries and must not be
  regenerated by the client after a response or connection failure.
- Idempotency does not replace authenticated user/device ownership checks; a
  device cannot use another account's stored operation outcome.
